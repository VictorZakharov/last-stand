# AGENTS.md

Guide for coding agents working on **Last Stand**, a browser 3D wave-survival ARPG (Three.js + TypeScript + Vite). `README.md` is the player/contributor overview; this file covers the things that aren't obvious from the code.

The heroes' models and legs have notes of their own in `docs/agents/` (`heads.md`, `heroes.md`, `ranger-bow.md`, `legs.md`), read before changing them; the gotchas below say which covers what. What is learned about one of those goes in its note: this file keeps what applies across the game, and stays under 120k characters (every agent's session loads it whole, and Claude Code warns past 150k); when it nears that, move the largest area into a note of its own.

## Commands

```bash
npm install
npm run dev          # Vite dev server, http://localhost:5173
npm run typecheck    # tsc --noEmit (strict)
npm run build        # typecheck + production build into dist/
npm run check:pages  # after build: every asset path must work under the Pages base path
npm run stalls       # the game in the installed Chrome, traced: the browser's own stalls (tools/stalls/README.md)
npm run icons -- sheet  # every class's skill icons side by side at a slot's size (check, add: tools/icons/README.md)
```

The game has no test suite. Verify changes with `npm run build` and by playing the dev build in a browser. A hero's face is measured against a reference picture with `npm run facelab` (`tools/facelab/README.md`; once: `npm run facelab -- --setup`). Pictures and measures of the game go through the lab (`tools/lab/README.md`): `npm run lab:serve` boots each command's page ahead of it (every command runs on a fresh boot and gives the same result every time), `npm run lab -- sheet` pictures the hero in the player's views with each arm's load beside them, `carry` measures the carried bow, `feet` the feet against the ground round the dais's edges and on level ground (standing at full draw, walking across, strafing drawn, running reversals: out of reach, wobbling, sliding, in a riser, the rhythm), `range` every joint against a body's ranges frame by frame (standing, walking each way, attacking, and walks that change direction while he attacks, held or tapped, or runs: each angle past its range, its worst and where, each scenario's fastest ankle, `--trace` the leg IK frame by frame as `gait --trace` lists it, each frame's joints past their ranges beside it), `coop` two games playing together, the host's and a guest's beside it, their messages carried as a link of a high ping and jitter carries them (`--ping`, `--jitter`: how far behind and how roughly each shows the other's heroes and foes, how its timeline plays them out, whether an arrow that struck a foe on the guest's screen counted, whether a blow it dodged hurt it, a guest brought down and raised, a guest's blink as the host's screen shows it: when it hid the copy, where the copy came out, the foes it dazed on both screens; `--class mage`), `stops` the hero coming to a stop from a run as a person stops (runs let go at different points of a stride, on level ground, drawn and by the dais's edges: the steps once still, a foot put out and drawn back, steps back, a foot on another level than the body's or stepped onto one once still, `--trace`, `--only`), `gait` the walk judged as a person's (level ground and the steps, nothing drawn, drawn, tapping, changing direction often and going round in circles: each foot's time on the ground against the plan, both and neither, the steps a second and their length, hops, a foot dance's short steps, the gallops (a foot leaving within 0.3 of a stride of the other's: counted as hops, both feet within a few frames, a gallop at every set-off went unseen), the steps' width, the hips' rise and fall, a planted foot dragged, each hand's swing against its knee half second by half second, the rhythm against the walk cycle, steps back under a body that stopped, the jerks, each step's swing against its plan and why it left, every frame judged as a body's: its centre of mass with its gear against the push its motion needs from the planted soles, in the air falling as a body does, and every joint within its range, `--trace` each frame (`--span` some), a scenario held up by a prop failing it, and a film of each round its first hop), `form` the run judged against a runner's (published runners' cadence, time on the ground, joint curves over the stride, lean, bounce and arm swing, at a man's size, with each way the hero holds his weapons: stick figures of his stride over a runner's, and the hero pictured from both sides, in the game's views and his arms close up, at eight points of it; the set-up's `--gear` holds them any way his class can), `probe <module>` runs a measure of your own on the lab's clock and set-ups, `check` runs every hero's checks of a change to how they move side by side (`--ab`: against main, its side kept once it has run; each gait scenario from three starts, its turns at other points of a stride, as a frame's change anywhere sends a scenario's later strides elsewhere: judge a change on the counts over all of them, each side's in the log), `ui` pictures the UI in its states (the lobby, a tooltip, How to play, the save slots, a class button clicked and a key pressed after it, the lobby's views switched with each label against its anchor through every glide, the run's HUD with a hurt foe's bar and damage numbers, the scores, the perf overlay, the choice after a wave, the pause menu, the summary) with each named element's and label's box as a share of the window, `touch` the touch controls' move stick pushed by a finger, its touches sent as a touch screen's (slid out through the stick's travel, to its edge and far past it, half the window across: the stick's push, the knob against the finger and the hero's speed, a push further out never giving less), `light` the frame's light as the player sees it (the hero standing in each biome, view and facing, the frame drawn and read back from the canvas: its light as a share of the screen's white, by thirds, its brightest pixels, near white and past it; `--hdr` draws each again in HDR and checks it against the SDR frame), `spawns` the foes coming in (boss waves one after another, a seed each: the gate every foe came by, its spot against the props, the gates each group and wave left idle, when the boss came against the rest of its wave, and its walk to the hero from each gate), `health` the low-Health look (the hero's Health held at shares of his most in each biome, view and facing: the colour drained, the blood's cover and how far in it reaches, nothing in the view's middle, more of both as the Health falls, none above where it starts), `held` every held skill's preview as the player holds it (ready, then through its cooldown and short of energy: its own look, red and counting down until a release would cast; Quarry Mark's outline round its foe in every view, its pixels near the foe and none away; Starfall's ring against its strikes, every foe inside it struck on every cast; every mark on the floor held across the dais's step, on each level and down its faces, none of it under the floor or standing off it; no shader compiled meanwhile), `blink` the mage's blink cast as the player casts it (open ground, past his reach, into a prop, past one, the arena's edge, onto the dais, his own feet: where it came out against its preview and his reach, the frames he was hidden and the blows that landed in them, the foes near and far it dazed and how they stood), `draw` each drawn shot held at full draw as the player holds it (the glint round its arrowhead every frame in every view: motes as it's drawn, held at full until it's loosed, and the pixels it lights as the player sees it), `cast` a skill cast as the player casts it, its effect seen frame by frame (each biome and view with the biome's foes coming at him, every frame drawn and read back: its light against the budget, the frame's mean every tenth of a second, the flashes in any second and the worst cell's light through it, the shaders compiled late), `gear` full sets of gear rolled for every class at each tier (the Health, regeneration and draught they give, and the damage they multiply), `--screen WxH@ratio` puts a command's page on a screen of that size and pixel ratio, `--screens a,b` runs it on two screens and compares them as `--ab` compares two commits (`ui --screens 3840x2160@1,1280x720@3`: a 4K screen at 100% and 300%), `--ab` runs any of them on `origin/main` too and says which lines and pictures differ (a commit against itself agrees, line for line), `--watch` runs one again on each change to the source, and `--profile` says where a command's time went; a command exits with 1 when it failed or found a problem (an error in the page, a canary missed). An A/B's pictures that differ are pictured where they differ (`tools/lab/out/ab/<command>/`), a probe can return moments pictured (`lab.picture`, or `lab.screen` for the screen as the player sees it, the page's UI over the game, whole or round one element; written as a sheet and compared in an A/B), and `page/timing.ts` times a method's calls by the browser's own clock (the page's `performance.now` is the lab's). Write a new measure in the lab (`tools/lab/examples/handSpeed.ts` shows its parts: the state it measures checked to have happened, a canary it must catch), never as a script with a boot and a clock of its own, and keep it: from its first use it is a lab command, or part of one that measures the same thing, never a probe left in `.tmp` (every harness is permanent). The probes and films this file and its notes name (the bow probe, the range probe, `legdet`, the zigzag and aim probes...) were such scripts and aren't in the repo: each is a measure to port into the lab the first time it's needed again, as the carry's was (`carry`). The lab's own code has unit tests: `npm run lab:test`.

## Workflow

- **Every change goes through a PR** from a branch off `main`; never push to `main` directly. Each PR gets a live preview at `https://victorzakharov.github.io/last-stand/pr-preview/pr-N/` (sticky PR comment), forks included: `pr-preview-build.yml` builds the PR with a read-only token, then `pr-preview.yml` (a `workflow_run`, always the copy on `main`) checks the artifact's PR number against the API and publishes it. Never run PR code in `pr-preview.yml`. Fork runs need the maintainer's approval on every push (repo setting "all external contributors"), so nothing from a fork publishes unseen. Merging to `main` deploys production (`deploy-pages.yml`).
- **`main` is protected:** PRs only, merged with a merge commit (squash and rebase merges are disabled), and the branch must be up to date. **PR branches must be linear:** `git rebase origin/main` to update, never merge `main` into a branch. The `branch-policy.yml` check fails any PR containing merge commits. Merged branches are deleted automatically.
- Pages is served from an aggregated `gh-pages` branch: production at the root, open PR previews under `pr-preview/`. Don't switch Pages to "GitHub Actions only" and don't delete that branch.
- Keep PRs focused on one feature.
- **Dokci relay TLS:** the production route in `.dokci/project.yaml` must explicitly set `entryPoint: websecure` and `certificateResolver: letsencrypt`. Omitting them creates an HTTP-only route even though the installed proxy redirects public HTTP to HTTPS; container health alone does not prove public TLS works. Keep the relay's internal HTTP port and health check unchanged, and verify trusted HTTPS at `/health` plus a WSS connection after the merged revision deploys. Never bypass certificate verification or add a public-relay fallback.
- **Don't waste compute: a check run over and over takes minutes, not half an hour.** The lab is run hundreds of times over a task, so a round's cost multiplies. Before running a suite again and again, ask what one round costs and what of it is wasted, and fix the tool first: profile it (`--profile`), keep what can't change (an A/B's other side is kept by its commit, `out/ab-cache`), run independent commands side by side (`npm run lab -- check --ab`: every hero's gait, stops and ranges, the ranger's feet and carry, in sessions of their own), skip what the measure never reads (films, pictures), and while iterating run only the scenarios a change can touch (`--scenarios`, `--classes`). Run one command at a time, both sides each time, the mage's cape (the heroes had capes then) stepped throughout and each gait scenario run again for a film, the same check took 31 to 35 minutes a round, and was run five times in a day.
- **When the work stops being smooth, stop and fix how it's done.** Running into the same wall again is the sign: a probe rewritten for each task, a result that turns out to have measured nothing, a restart before every measure, a hand-made swap to compare with `main`, a constant edited and reloaded over and over. Take the time then to build the proper tool, harness or refactor, typed, reused and documented in `tools/`, instead of one more quick script that might work. This repo keeps a high quality bar, and its tools are held to it too: an iteration should take seconds and its results should be trustworthy. (On the bow's carry, seven one-off probes in `.tmp` each re-copied the boot, the fixed clock and the ray tests; two reported clean while measuring nothing, and one issue took hours. `tools/lab` replaces them.)
- **A pose is decided as a person would hold it, then looked at as the player sees it, and only then measured.** Say what a real body does first (an archer between shots: the arm hanging straight, the bow level, the arrow pointing down), rig that directly in those terms (directions and joint angles, not a search over rotations), and look at it in the game's own views (the lobby's camera, the run's, close-ups from the front, the side and behind) in the state the player sees it in (an arrow on the string, standing and at both ends of a stride) before running any clip measure. Clip measures check a natural pose; they never choose one: a few millimetres of clip in a pose a body would take beat no clip in one it wouldn't (a bow carry chosen from a hundred by its clip count held the arm out from the side with the arrow sticking out sideways, and took hours).
- **A/B against `main` without losing work:** commit what you have first (a `wip:` commit, squashed or reworded before the PR), and only then swap files: `git checkout origin/main -- <files>` to measure main, `git checkout HEAD -- <files>` to come back, and `git status` clean after. Never run `git checkout <ref> -- <file>` (or `git restore`, `git reset --hard`) over uncommitted changes, and don't use `git stash` as the swap: with a clean tree it stashes nothing and both sides of the A/B measure the branch, and checking a file out before stashing it throws its changes away (both happened, and an afternoon's tuning was lost).
- **Prompt starts with `new issue:`** (fork workflow): run `scripts/issue.sh "title" "description"` with a title and description you write from the prompt, then do the work on the branch it creates. When done, run `scripts/commit.sh "PR title" "PR description"` instead of committing yourself, and reply with the PR link.

## Product rules

- **Core loop:** after *every* wave the player chooses Bank (keep all loot, leave) or Continue (harder wave, better loot). Dying loses all unbanked loot. Loot is **hidden until banked**: nothing drops on the floor, items go straight into the run's bag (`gainLoot` in `game/run.ts`), and the HUD shows only counts per rarity. The bank summary reveals the items one by one, the most valuable first, each in its place in the list. Don't show what an unbanked item is (name, base, stats) anywhere. Don't change this without being asked.
- **The lobby floor** (`game/groundItems.ts`): gear given up in the lobby (dragged onto the game field, Shift-click, the touch sheet's Drop) is thrown on the floor, not deleted. Clicking its name (drawn with the other overlays and picked on the canvas, `bindPicking`: the press never reaches the game; on touch a tap shows the card, a second tap takes it) puts it back in the stash, if the class can use its base and the stash has room. In co-op every game shows every drop and the host decides who got one first (`gdrop` / `gtake` / `gtaken` in `net/session.ts`). Whatever is left on the floor is lost when a run starts, and a guest leaving the room leaves it to the host. Every drop is drawn by three instanced meshes, one a piece (its shard, the glow under it and its shaft of light), each drop coloured by its rarity and each piece drawn in one pass: as meshes of their own a drop cost 8 draw calls (additive and double-sided, three.js draws each twice), and 120 drops added 10 to 14 ms to a frame.
- **Everything is procedural.** No downloaded models, textures or audio: geometry, canvas textures, rigs/animation, VFX and WebAudio sfx are generated at runtime. Don't add binary assets. The exceptions are screenshots in `docs/`, the painted skill icons (`src/ui/skillArt/`, see below) and the music (`src/audio/music/`, see below).
- **Originality:** this is open source. Skill, item, enemy and class names must be original. No Grim Dawn (or other game) names, trademarks or assets.
- The game is class-agnostic by name ("Last Stand"). More classes are planned, so keep class-specific code in class data, models and skills, not in the shared systems.
- **The UI must fit any screen size, desktop and mobile.** Anything that overflows or overlaps at some viewport size is a bug.
  - Scale: `--ui` for the lobby and modals, `--hud` for the in-run HUD, `--touch` for the touch controls (all set in `src/ui/scale.ts`, which `uiScales` exports for code).
  - **The UI is a share of the screen, whatever the OS's scaling**: a 4K screen shows it the same at 100% as at 300% (the fit has no ceiling: capped at 1.35, the UI at 100% was half its size at 300%). Only small screens (phones, small windows) keep a floor in css px, so they stay readable, and the touch controls are sized for a finger in css px. Everything drawn over the screen follows it: the tooltips' cards (`zoom`), the world's labels (drawn at `--hud`, the floor's names at `--ui`: their art is in px of the reference layout, `Label.sizedBy`), and the loading screen, styled before any script runs (its `--u` in `index.html`, the same fit in CSS). An element scaled with `scale:` keeps its offsets from the screen's edges unscaled, so give them as `hud()` too; a `zoom`ed one's are zoomed with it. Check with `npm run lab -- ui --screens 3840x2160@1,1280x720@3`: the same lines, and pictures apart only by text's antialiasing (the lobby's text drifts up to 1% of the screen down a panel: Blink rounds each line of text to whole css px).
  - Layouts: on desktop the lobby is a CSS grid `[left | center loadout | right]` with the panels against the screen's edges; each folds away to its edge on its own, leaving a labelled tab (`FOLDS` in `ui/menus.ts`, kept in `localStorage`). A fold tab stands outside its panel's frame, so a panel that scrolls does it inside (the left one's `.ml-body`), never on the panel itself. Short screens (phones held sideways, height ≤ 520) and upright tablets show one panel at a time, picked from `#lobby-rail`, and the camera view shifts so the character stays beside the panel (`lobbyViewShift`); they never fold a panel. Phones held upright get a "turn your device" overlay.
  - Nothing moves as the class changes: text that differs by class is laid over the other classes' in one grid cell, only the current one shown, so its box is the largest's (the class card's name and tagline: the warrior's name pushed the class buttons onto a line of their own and the ranger's tagline took two lines, the panel growing by up to 40 px).
  - Check desktop at 1024×700 and 1920×1080, a phone at 844×390 and a tablet at 1180×820 and 820×1180 (Playwright with `isMobile` + `hasTouch`).
- **Installable, offline (PWA):** `public/manifest.webmanifest` plus a build plugin (`scripts/pwa.ts`, production builds only).
  - Install: Chrome and Edge fire `beforeinstallprompt`, and the lobby's Install link opens it. Safari (iOS) and Firefox never fire it, so on phones and tablets the link is always shown (unless already running installed) and opens `#install`, the add-to-home-screen steps for that platform.
  - The plugin renders the PNG app icons from `public/icon.svg` at build time (no binary assets in the repo) and writes `dist/sw.js`, which precaches every built file.
  - The worker's cache name is a hash of the build, so each deploy installs its own cache (fetched past the HTTP cache: Pages sends `max-age=600`) and takes over at once. It keeps the previous build's cache, so a page still running the old build can load its remaining chunks.
  - **A plain reload must show a new deploy:** the page is served network-first (the cached copy when offline or after 4s), the built files cache-first. `src/ui/pwa.ts` registers the worker (`updateViaCache: 'none'`, checking again when the tab comes back into view), shows the Install link and offers a reload in the lobby when a new build took over an open page (it asks the worker which cache it serves). Production's scope contains the PR previews, so the worker skips `pr-preview/` paths (each preview registers its own).
  - The pause menu shows the build (`__BUILD__` from `vite.config.ts`: commit, a preview's PR number, the build time in local time).
  - Test offline behaviour with `npm run build` + `vite preview`: the dev server has no worker.
- **Touch** (`src/ui/touch.ts`): touch mode (`body.touch`, `input.touchMode`) follows the last pointer used, and the browser's emulated mouse events are ignored in it.
  - Controls: a move stick on the left half and the skill buttons on the right. The stick's travel is its size as drawn (`--touch`), its knob under the finger, full speed from 0.6 of the travel and however far past its edge the finger goes (held to the edge and divided by the finger's whole distance, half a screen out walked the hero at a seventh of his speed; check with `npm run lab -- touch`, on a phone's `--screen` too). Tap casts at the nearest foe; drag aims by hand and casts on release. The basic attack and channels act while held.
  - A control clicked or tapped gives its focus back (`ui/focus.ts`): left focused, a class button showed the browser's focus ring at the game's next key, clipped by its group's frame to a second border down its side, and Space or Enter pressed it again. Check with `npm run lab -- ui --states clicked`.
  - Everything hover-only needs a touch path. Tooltips open on tap (`bindTooltip`); items open an action sheet (`openItemSheet`); skills are bound by tapping a key and then the skill. Drag and drop and Shift are desktop extras.

| `src/fx/` | CPU particle pools, a fixed pool of 8 point lights (`lights.ts`), transient effects (`effects.ts`) |
| `src/core/` | Renderer + post chain, input, audio, procedural textures & materials, game-time scheduler (`timers.ts`) |
| `src/net/` | Co-op: who simulates what (`role.ts`), the links (`transport.ts`: our relay server, `server/relay`, or `?net=local`), rooms, lobby and each player's own state (`session.ts`), the host's reports of the fight (`sync.ts`) |
| `src/ui/` | DOM HUD, lobby/menus, tooltips, loadout editor, item icons (inline SVG), skill icons (`skillArt.ts`), attributes; the stylesheets (`styles/`, SCSS); the world's overlays, drawn in WebGL over the frame (`overlay/`, placed by `floaters.ts`) |
| `src/state.ts` / `src/events.ts` | Typed global state `G` and a typed event bus |

**Adding a class:** a data file in `src/data/classes/` registered in its `index.ts`, a model in `entities/models/`, and skills in `combat/skills/`. Class data also sets the lobby accent, the loadout panel title, the cast-point light and item base names; give new bases an icon in `ui/itemIcons.ts` and the class an equipment silhouette (`#equip .doll[data-class]` in `index.html`). Classes share no progress: each has its own profile. Switching class in the lobby rebuilds the `Player`, and `game/warmup.ts` builds every class's model at boot with everything it can wear shown at once (a hidden mesh compiles nothing), so a class switch or equipping anything compiles nothing. A switch builds the new hero from scratch, all but his head: its geometry is made once per face, hair and detail (`once` in `models/head.ts`: the hair's cards were 60% of a build, which took 95 to 170 ms, now 30 to 70) and shared by every build after (`userData.shared`, which a model's dispose keeps: `disposeGeometries` in `rig.ts`). Time a switch in the lab's lobby (abandon the run its set-up starts) by the browser's own clock, `__labClock.realNow`.

**Adding a biome:** an entry in `data/biomes.ts` (enemy pool, boss, minimap), a builder in `world/` registered in `arena.ts`, and its enemies in `data/enemies.ts` with models in `entities/models/`.

## Gotchas

- **NaN means black lines or boxes on screen.** Bloom smears NaN/Inf pixels across the frame. Known causes: GLSL `smoothstep(a, b, x)` with `a >= b` (it's undefined, so write `1.0 - smoothstep(b, a, x)`), and `atan(0, 0)`. `renderer.ts` has a sanitize pass before bloom as a safety net; still fix the source.
- **Bright effects:** light adds up, so the final grade (`core/renderer.ts`) compresses it the way the eye does, and effects and their lights stay at full strength: don't dim single effects to fix a bright scene.
  - **Adaptation:** after bloom, the average light over a 16x9 and a 4x3 grid of the frame (`AreaPass`) is held under per-view targets (`ADAPT`, just above each view's ordinary scenes, which it leaves untouched) by compressing only the light above `ADAPT_BASE`, on a power curve. Never scale a whole pixel by its area's brightness (the dim ground round an effect darkens into a shadow around it), and don't adapt before bloom (effects drop under bloom's threshold and turn into flat discs with no glow). Above `HI_KNEE` the brightest channel eases towards `HI_CAP`, and in a large glare tone mapping keeps a bright pixel's colour (`HUE_*`, `GLARE_*`), so a big bright area stays green or blue instead of turning white.
  - **Distance:** effect materials dim with their distance from the camera (`nearGlow` in `core/materials.ts`: full strength from the top-down camera's distance, down to a quarter up close). `additive()`, the glow particles, projectile cores (a hostile bolt's is an orb of added light, with a pooled light when one is free; the spore throwers' are `fx/sporeOrb.ts`, the Rift Witch's and the Colossus's `fx/riftBolts.ts`: blended orbs, with added-light tails and halos), entity glows (`kit.glow`, the staff orb included; a hero's gear glows opt out) and the hit flash on bodies have it; wrap a new effect material in `nearGlow()`. The world's own glows don't.
  - **First person:** particles fade within 3.5m of the camera, a bolt flying at the camera shrinks away over its last metres (never pops out: nothing near the camera may switch off at once), and a cast leaves from `Player.castPoint` / `palmPoint`, which in first person are the weapon and hand in view. Keep lights off the camera: above the head, not at 2m. An effect round the body (a heal, a war cry) is seen from inside it: `Player.eyes` tells a skill it is, so it can put its particles where they're seen (a wider ring) and its light ahead of the view (`Player.lightAhead`; straight above, the weapons' steel mirrors it back into the view).
  - Nothing large may flash or pulse faster than about 1.5 times a second: 3+ flashes a second is a photosensitivity hazard. A hit's flash on a body is full at most every 0.7s (`hitFlash` in `util.ts`). A pattern moving across the view flashes too: Maelstrom's wide ribbons passing a point 4 times a second, and its lashes of lightning at every damage tick, each flashed a sixteenth of the screen 3 to 4 times a second.
  - **Measure an effect** with `npm run lab -- cast <skill>` (`--class`, against main: commit, swap the skill's files in from `origin/main`, run, swap back): every frame of it drawn and read back in each biome and view, with the biome's foes coming at the hero. Its light is held to the budget from the owner's screenshots (it raises the frame's mean by 50 at most, its brightest sixteenth 150, 5% of the frame bright, as stored), its flashes are counted as WCAG counts them (a sixteenth of the screen each), and the shaders compiled after loading must be none. Read its timeline before changing anything: a mean that leapt as Maelstrom's first tick landed in first person was a dark foe in front of the camera dying, and a bright rock behind it showing.

- **HDR output** (`core/hdr.ts`, the pause menu's HDR: Auto or Off): on a display in HDR mode (`dynamic-range: high`) the frame's highlights go past the screen's white, and everything under them shows as on an SDR screen.

A symmetric emblem is laid out exactly, as with a compass and a ruler: its pieces identical and evenly placed, its rings true circles, its steel smooth (Quarry Mark's first reticle, four arrowheads of different sizes with hooked barbs on a lumpy, smoky ring, looked messy), and a target keeps its middle black, with bold bright rings round it and a bright point in it (its middle filled with orange glow, a steel hoop read as a furnace with a crosshair at slot size).
    - **Padded:** the touch buttons are round, so 99.5% of an icon's light must lie inside the circle they draw, and its content at least 4% clear of the square's edges. The ranger's arrows ran corner to corner and the circle cut up to 16% of their light. On a black background a picture is padded exactly by shrinking it onto a larger black square, which `npm run icons -- add <impl> <original>` does as it writes the WebP (`tools/icons/README.md`); `check` measures every icon (most of the warrior's and mage's, made before this rule, reach past the circle, Twin Fangs and Raise Shield by 10% of their light).
    - **Coloured apart:** each skill of a class in a colour of its own, as the warrior's and mage's are, with `icon.color` (the tooltip's name, the key diagram's glow) set to match. Veilstep's is violet though its light in the game is green: Void Lance's icon is green.
    - **Judged at slot size:** compare it with the others shrunk to 60 px (`npm run icons -- sheet --try <impl>=<picture>`: each class's icons side by side, large and at 60 px square and round, the candidate in its place). The ranger's first set was crowded (vines, sparks, a stag behind the reticle), and the next came out as thin, pale arrows that faded beside the others.
    - **Tooling:** the ranger's and Veilstep's were made with Codex CLI's image generation, attaching icons of the set as style references (`codex exec -i <icon> ...`): the warrior's for crafted objects, the class's own for its look, and the accepted ones of a set being made. Ask for two designs of a new one: the first idea isn't often the one.
- **Asset paths:** Vite `base` is `./`. In `index.html` reference assets root-absolute (`/favicon.svg`) so Vite rewrites them; `check:pages` fails on paths that would break under `/last-stand/pr-preview/pr-N/`.

- **Co-op** (`src/net/`, rules in `game/run.ts`, UI in `ui/coop.ts`):
  - **Who runs what.** Every game moves and casts its own player and reports it (`pl` state at `COOP.sendRate` with its life, `ev` actions: cast / fire / channel start and stop, a hit it took, its fall), in the lobby and in runs; the others replay it on a remote `Player` (`local` false, `replay()`, `updateRemote`). The host's game simulates the fight (enemies, loot, waves, downs) and reports it (`net/sync.ts`: events every frame, a snapshot at the send rate); a guest's enemies are copies (`Enemy.net`) that don't think. **Each game judges its own hero's hits, both ways, as its own screen shows them:** what its skills hit it deals there and then (on a guest, on its copies: the foe's life and a kill show at once, and the hits go to the host on `dmg`, which deals them on its foes and says in its snapshots how far it has, so the copy's life is the host's less the hits still on their way), and a foe's blow at it is judged where it stands against the foe as it shows it (`FX.melee`, `FX.slam`, a bolt's projectile on every game: a hit on a partner's copy does nothing). Judged on the host at 300 ms, 4 of 6 arrows that struck a moving foe on the guest's screen missed it there (it had moved on a metre), and 4 of 5 blows the guest dodged on its screen hurt it. A guest predicts its own fall as the host will rule it (`onPlayerDied`).
  - **Every message is stamped with its sender's clock and played out on a timeline** (`net/timeline.ts`): each partner's reports are shown a little behind the freshest one (`Timeline`: the reports' spacing and the lateness 98% of messages come within, its clock eased onto that place at most 5% fast or slow), positions read between reports (`Track`, a cubic through each report's position and velocity), events applied in order when their time comes (`Playout`: a partner's shot leaves as its body turns to it, a foe's blow lands as its swing shows, and is judged against that), past the last report carried on along its way a moment and then eased onto the next (`Smoother`). Shown as each report arrived, every copy jumped forward and stalled with each burst of a jittery link (speeds off by 1 to 1.4 m/s); eased onto a place that wobbled with the link's delay, a copy ran up to 10% fast or slow; stopped dead in a stall, it lost 0.6 m/s on its speed in under 1% of frames. Measure with `npm run lab -- coop` (`--ping`, `--jitter`) against `main`.
  - **Anything with gameplay effect goes through the checks in `net/role.ts`:** `hitEnemy` needs `by` (the casting player: its stats, the kill, leech) and only deals damage where `dealsDamage(by)` (its own game's), as `dazeEnemy` only dazes there; `hurtPlayer(p, ...)` only on the local player; props wear down where `hurtsProps(by)` (the host's in a run). Skill code runs on every game for its visuals, so keep its damage in `hitEnemy` and its hits on players in `hurtPlayer`.
  - **An enemy attack goes through `fx()` in `enemyAI.ts`** (named `FX` entries with numeric arguments), which guests replay on the host's timeline, with what each game needs to judge its own hero's hit in it (`melee`'s target slot and damage, `slam`'s damage and type). New attacks go there.
  - **Hooks, not imports:** the host reports through sinks set by `net/sync.ts` (`setSpawnSink`, `setFxSink`, `setNumberSink`, `setHitSink`, `runHooks`), so solo code has no network dependency and the relay library only loads when a room opens.
  - **Enemies target `e.target`** (the nearest active player, `nearestPlayer`), with a flow field per player slot. Use `G.players` (the local player first) for anything that concerns every player, and `G.player` only for the local one.
  - **A downed player** lasts `COOP.bleedOut` (25 s), its clock stopped while a teammate holds the revive key by it (`updateDowned`, the host's: the guests are told each one's clock in the snapshots), and is raised in `reviveTime` (2.3 s). Its partners see it marked (`markDowned` in `ui/coop.ts`, drawn over every other overlay, `ORDER.marker`): a red ring over the body with its clock running out round it and the seconds in it, beating like a heart as each one goes (harder in the last 8, a glow alone with reduced motion), the revive filling it in gold, how far it is, and off screen the same ring at the screen's edge on the way to it with an arrow pointing there (a small ring over the body alone was lost as soon as the body was off screen); in reach, a prompt low in the middle of the screen with the key to hold and the revive's bar (`promptRaise`; touch has its button). Look at it with `npm run lab -- coop --scenarios down --pictures`.
  - **A remote player has no staff light** (another point light would recompile every shader); its model is already warmed with the other classes.
  - The pause menu doesn't stop a co-op game (`G.menuOpen` with `G.paused` false; the local player goes `idle`), and a host in a background tab keeps stepping on a timer.
  - Bump `PROTOCOL` in `session.ts` (and the app id in `transport.ts` if the link itself changes) when the messages change: rooms only hold one version.
  - Test locally with two tabs of one browser and `?net=local` (a BroadcastChannel instead of the server): open a room in one, then open the invite link in the other.
  - **The relay server** (`server/relay/relay.mjs`, `ws://host/room/<app>/<code>?id=<peer>`): every game meets on it and every message goes through it over one WebSocket, JSON text frames; no public relays, STUN or TURN servers, and with it down there's no co-op (don't add a fallback to public ones: the owner wants only our own trusted server). Peer to peer over public Nostr relays, a player on a mobile carrier's network in Asia met the host and then never connected (ICE failed both ways: that needs a TURN server), so the server does both jobs on 443, through any network a page reaches. It checks the page's `Origin` (`ORIGINS`), holds 4 peers a room, caps each socket's messages and bytes a second, answers the game's pings (the round trip), and holds a dropped peer for `GRACE` so a reconnect with the same id is unseen. A restart loses its rooms: every game reconnects on its own for `RECONNECT`, and a partner missing after a reconnect has `GRACE` to come back before it counts as gone (told at once, the guest took the host as gone and left the room before the host was back). Dokci deploys it from `.dokci/project.yaml` (`server/relay/compose.yaml`, routed by Traefik to `ls.wellscoped.dev`) on every push to `main`. The game is built for `VITE_COOP_SERVER` (default `wss://ls.wellscoped.dev`), `?server=` tries another, and the invite link carries it. The co-op dialog asks the server's `/health` as it opens (`serverUp`, which the server answers with CORS for its `ORIGINS`) and, with no answer, says the server is offline, with Try again, Host and Join disabled; a room that can't reach it says the same (`ServerDown`, `SERVER_DOWN`), not an error. Test locally with `cd server/relay && npm i && ORIGINS=http://localhost:5199 PORT=8787 node relay.mjs` and `?server=ws://localhost:8787`, two browser contexts driving the page's own UI (an `import()` from a probe can get a second copy of a module), and a restart of the server under a joined room.
  - **The scores** (`ui/scoreboard.ts`, held on Tab; on touch a button under the pause button), in a run and a co-op lobby: each player's run in numbers (`game/stats.ts`: damage dealt, taken and blocked, healed, kills, downs, partners raised; the local player's counted as its own game judges its hits, a partner's as its game reports them on `st` once a second, from each run's start), its round trip to the co-op server with the minute before it as a graph (the server is pinged once a second), and for a partner how far behind its own game it's shown (half of both round trips and its timeline's wait). The lab's link reports a round trip as the relay's pings would, so `coop --pictures` shows it (`shoot`'s last moment, the host holding Tab).
  - **Diagnostics** (`net/netlog.ts`, the pause menu's "Show network stats", `ui/netHud.ts`): the link to the server (open, dropped, its round trip), the partners, the session's steps, in a report copied or shared from the overlay or the co-op dialog.

## Style

- TypeScript strict. Keep data (`src/data`) separate from behaviour, and type new data against `types.ts`.
- Match surrounding code: short header comment per file, sparse comments explaining *why*, compact one-line helpers where the file already uses them.
- **Tools (`tools/`) are written to be read**, as code we'd show anyone: one statement per line, lines under 120 characters, named functions and types instead of long inline chains, small modules with one job each, and a doc comment on everything exported. No chains of statements joined by semicolons on one line, no one-letter names beyond loop indices and coordinates. A harness is how the game's quality is judged, so it is held to a higher bar than a quick script.
- Styles are SCSS in `src/ui/styles/`: one partial per area (`_hud.scss`, `_lobby.scss`, `_modals.scss`...), imported by `index.scss` in cascade order (later files override earlier ones; a moved rule can change what wins). Use the theme (`_theme.scss`: colours named by role, not by hue, so a theme change stays in that file; surfaces; `ui()` / `hud()` / `touch()` scale helpers) and the mixins (`_mixins.scss`: frame, gem, corner brackets, diamond rule, section heading) instead of copying values: plain colours as `var(--frame)`, translucent ones as `rgba($frame, .35)`. The loading screen's styles stay inline in `index.html`. UI scales via the `--ui` variable. Honour `prefers-reduced-motion` for decorative animation.
